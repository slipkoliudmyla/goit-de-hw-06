# Spark Streaming — віконні алерти сенсорів

Домашнє завдання 6 курсу Data Engineering. PySpark читає JSON-події з Kafka, обчислює середні значення за ковзними вікнами, порівнює їх із правилами зовнішнього CSV й записує алерти у Kafka.

## Вимоги

- Java 17 і Python 3.12.
- `pip install -r requirements.txt` — PySpark 3.5.3 і kafka-python 3.0.11.
- Запущений Kafka; перевірено Kafka 3.9.1 на `127.0.0.1:19092`.
- При першому запуску Spark завантажує офіційний пакет `org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.3` із Maven Central. Версія конектора відповідає версії Spark.
- [LOCAL_KAFKA.md](LOCAL_KAFKA.md) пояснює запуск окремого навчального брокера. Якщо він уже працює для ДЗ5, другий брокер запускати не потрібно.

## Запуск

Кожен процес запускати в окремому терміналі з каталогу проєкту. Встановіть `JAVA_HOME` на вашу JDK 17. Для локального запуску можна також встановити `SPARK_LOCAL_IP=127.0.0.1`.

```sh
python create_topics.py
python consume_alerts.py
python streaming_alerts.py
python producer.py --sensor-id sensor-1
python producer.py --sensor-id sensor-2
```

Один запуск генератора — один сенсор зі сталим ID. Запис містить `id`, `temperature`, `humidity`, `timestamp` (Unix seconds). Температура генерується випадково в межах 25–45, вологість — 15–85. За замовчуванням генератор працює без обмеження; Ctrl+C його зупиняє.

Для повторення задокументованого короткого запуску використані два генератори:

```sh
python producer.py --sensor-id sensor-1 --seed 5 --interval 15 --count 10
python producer.py --sensor-id sensor-2 --seed 6 --interval 15 --count 10
```

Спочатку запустіть Spark і дочекайтесь `STREAM_STARTED`, потім обидва генератори. Відтворюються випадкові значення; часові мітки та точний склад початкового часткового вікна залежать від моменту запуску. Для автоматичної зупинки Spark є `--run-seconds 190`; без цього параметра потік працює до Ctrl+C.

## Налаштування

`KAFKA_BOOTSTRAP_SERVERS` за замовчуванням `127.0.0.1:19092`; `KAFKA_TOPIC_PREFIX` — `slipkoliudmyla_hw06`. Створюються `slipkoliudmyla_hw06_building_sensors` і `slipkoliudmyla_hw06_alerts`, по 2 партиції з replication factor 1. Підключення локальне й не потребує паролів.

`alerts_conditions.csv` — оригінальні дані [CSV з умови GoIT](https://drive.google.com/file/d/1TBrcwoEsPR_7WyPZY7rIyQelB-8NZa3F/view?usp=sharing):

| code | Активна умова | message |
| --- | --- | --- |
| 101 | вологість 0–40 | It's too dry |
| 102 | вологість 60–100 | It's too wet |
| 103 | температура −300–30 | It's too cold |
| 104 | температура 40–300 | It's too hot |

Межі включні (`between`). Пара `-999,-999` вимикає перевірку відповідного показника. Якщо активні обидва показники одного правила, мають виконуватися обидва діапазони. Одне вікно може відповідати кільком правилам. CSV зчитується як статична таблиця під час запуску; для зміни правил відредагуйте CSV й перезапустіть Spark із тим самим checkpoint. Змінювати програмний код не потрібно.

## Як обчислюються результати

- Час події перетворюється на Spark timestamp зі збереженням дробових секунд; сесія працює в UTC.
- `withWatermark("event_time", "10 seconds")` застосовується до агрегації.
- `window("event_time", "1 minute", "30 seconds")` задає 60-секундні вікна з кроком 30 секунд; інтервали мають вигляд `[start, end)`.
- `avg` рахує температуру та вологість для всіх подій будівлі у вікні; ID сенсора не є ключем групування.
- Використано append mode: у вихід потрапляють остаточні вікна, які вже закрив watermark. `foreachBatch` отримує ці підсумки, виконує cross join із CSV, фільтрує та пише JSON через Spark Kafka sink.
- Якщо події припинили надходити, watermark не рухається від самого очікування. Останні відкриті вікна залишаються в checkpoint до надходження новіших подій. Це очікувана поведінка.

JSON-алерт містить `window.start/end`, `temperature_avg`, `humidity_avg`, `event_count`, `condition_id`, `code`, `message`, `timestamp`. Це описові назви середніх значень, які в ілюстрації завдання позначені як `t_avg` і `h_avg`. Ключ Kafka складається з початку/кінця вікна та коду правила.

## Перевірка

Після зупинки генераторів і завершення доступних мікробатчів:

```sh
python verify.py
```

Перевірка читає Kafka без зміни consumer offsets, незалежно перераховує всі закриті вікна та порівнює кожен алерт. Додатково Spark-тест охоплює всі чотири правила CSV, включні межі, вимкнені показники й нормальні значення без алерту.

Під час зафіксованого запуску два сенсори надіслали по 10 записів; закрито 4 вікна й прочитано 3 алерти коду 102. Усі середні збіглися з вхідними даними; у цьому запуску немає пропущених чи повторних алертів. Це результат перевірки конкретного запуску, а не гарантія exactly once після збоїв: Kafka sink і foreachBatch можуть повторно записати дані при відновленні. Стабільний ключ може бути основою для окремої дедуплікації.

Checkpoint за замовчуванням `checkpoints/sensor-alerts`; `--checkpoint` дозволяє задати окремий шлях. Повторний запуск із тим самим checkpoint продовжує збережений стан. Не використовуйте один checkpoint для різних запитів або наборів топіків.

У `evidence/` — DOCX-звіт, скриншоти браузерного переглядача реальних stdout-потоків, сирі журнали та `verification.json`. Значення у скриншотах походять із виконання, а не з макета термінала.
